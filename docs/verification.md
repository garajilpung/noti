## 통제된 예시 검증

실제 업무공간과 분리된 고유한 검증 업무공간에서 다음을 확인하고 검증 자료를 정리했다.

1. 기관 등록 → 최초 수집 → 기준 자료 저장.
2. 재점검 시 중복 공지·알림 방지 및 수집본 보관.
3. 신규 공지 1건과 기존 본문 변경 1건의 구분, 전후 내용 보존.
4. 실패와 변경 없음 구분, 실패 시 기존 기준과 최근 성공 시각 유지.
5. 업체·프로젝트 각각 여러 기관 연결 및 공지 직접 연결.
6. 확인 완료 + 검토 필요 + 메모 + 연결 + 이력 + 변경 시각 저장.
7. 새로운 DB 연결에서도 저장 내용 유지, 업무공간 분리.
8. 당일 성공 점검 시 예정 일정 완료 처리.
9. 동일 기관 동시 실행 차단 및 다른 기관 점검 지속.

추가 단위 검증: 본문·제외 영역, 공백 정규화, 제목 수정 감지, 공지 URL 정규화, 게시일 추출, HTTPS·내부 주소 검사, NAT64 처리, KST 날짜, 기준 자료의 수동 업무 지정, 요청 출처 검증.

## 실제 브라우저 확인

- 캘린더에 실행 날짜별 기관·예정·완료·실패를 표시.
- 검증용 업체와 프로젝트를 각각 등록하고 기관 두 곳을 연결. 새로고침 후 저장 내용 유지.
- 실제 공지 상세에서 확인 완료 + 검토 필요, 검증 메모, 업체·프로젝트 연결 저장 후 새로고침하여 유지 확인.
- 공지 검색과 기준 자료/업무 알림 필터 확인.
- 캘린더 점검 일정 등록 → 해당 날짜 표시 → 지금 점검 → 실제 기관 수집 → 일정 완료 반영 확인.
- 검증용 업체·프로젝트·일정과 테스트 메모·이력은 정리하고 기존 처리 상태를 복원. 실제 수집 이력은 보관.
- 좁은 화면의 반응형 캘린더 확인.

## 확인 범위의 한계

24개 기관의 홈페이지 URL 24개와 공지 URL 24개에 읽기 요청을 보냈다. 각 종류에서 22곳은 HTTP 200, 경찰청·eFine 2곳은 307 리다이렉트가 반복됐다. HTTP 200은 접속 응답의 확인이며, 본문 추출과 업무 저장 성공을 뜻하지 않는다.

목록·본문의 실제 수집은 위 3곳만 확인했다. 다른 21곳의 수집은 연동 준비 상태다. 실제 기관에서 신규 공지 또는 본문 수정이 발생하는 상황은 이번 점검에서 관찰되지 않았으며, 해당 감지는 통제된 예시 자료로 확인했다.

첨부파일 내부 내용, 같은 URL의 외부 이미지 교체, 이전 페이지로 이동한 공지의 재수정은 감지 범위에서 제외한다. 자동 정기 점검과 사용자별 로그인·권한은 활성화하지 않았다.

전체 URL의 접속 결과는 [기관별 URL 검증표](url-checks.md)를 참고한다.
